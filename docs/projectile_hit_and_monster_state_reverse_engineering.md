# 子弹命中与怪物状态逆向实现方案

更新时间：2026-08-28

逆向基线：荣耀版 `starhome_lz_ry` 客户端 FCC 与已导出的荣耀版素材

适用工程：`starhome_remake`

## 1. 结论摘要

### 1.1 子弹并非全部由客户端判定，也没有证据表明服务器按显示帧逐颗计算

荣耀版采用的是一套年代较早的“客户端表现模拟 + 服务端伤害结算 + 不同武器使用不同上报协议”的混合方案：

- 客户端立即播放开火动作、创建子弹、按照本地时间推进弹体并做表现碰撞；
- 子弹在本地碰到怪物时，可以立即消失，因此看起来像被第一个怪物“接住”；
- 本地表现碰撞不直接修改怪物血量；
- 怪物实际扣血来自服务器回调，回调中直接携带伤害值、命中特效索引、声音索引和调色板索引；
- 怪物死亡不是客户端看到血量归零后自行推导，而是另一条 `OnDie` 生命周期消息；
- 能量炮、火箭炮、导弹的上报方式并不统一，原版协议存在一定程度的客户端信任，不能原样照搬到复刻服务端。

对复刻版最重要的结论是：

> 客户端碰撞只能负责“看上去撞到了”；服务端碰撞才有资格决定“究竟打中了谁、何时扣血、是否死亡”。

服务器不需要以客户端 60 FPS 之类的显示帧率同步所有弹体。几个人私下联机的规模下，服务端以固定 20 Hz 推进权威弹体，并在每次逻辑步中做连续线段碰撞，已经足够准确；客户端仍可用显示帧率平滑插值。

### 1.2 怪物三态的权责划分

怪物的“移动、攻击、站立”不是纯客户端 AI：

| 内容 | 原客户端实际职责 | 服务端职责判断 |
|---|---|---|
| 是否移动、走哪条路 | 收到路径字符串后插值播放移动动画 | 决定路径、速度与开始移动时机 |
| 行走中的逐像素位置 | 执行 `path(...)`，本地连续插值 | 至少持有/下发权威路径与速度 |
| 何时攻击、攻击谁 | 收到 `OnNpcAttack(x,y)` 后朝向目标、播放攻击动画并生成子弹表现 | 决定目标、攻击时机和伤害 |
| 站立动画 | 路径或攻击动画播完后，本地自动切回并循环播放 | 逻辑上没有新动作时保持空闲 |
| 受伤 | 播放服务器指定的命中特效，按服务器给出的值刷新血条 | 决定命中与伤害值 |
| 死亡 | 收到 `OnDie` 后播放死亡效果并隐藏本体 | 决定死亡、掉落、经验、复活等生命周期 |

因此可以把原版理解为：服务端控制怪物的游戏状态，客户端根据离散命令完成连续动画；“站立”有一部分是客户端动画机的自然回落，但并不代表客户端有权决定怪物停止战斗。

## 2. 证据等级

本文使用以下标记：

- **已确认**：荣耀版客户端代码中存在直接证据；
- **高置信推断**：客户端接口边界清晰，但没有服务端源码，内部算法只能由协议反推；
- **待抓包确认**：仅凭 FCC 无法区分两个均可行的服务端实现。

必须保留一个边界：目前只有客户端 FCC，没有原服务端源码。因此能非常确定“客户端没有做什么”和“服务端必须返回什么”，但无法从静态客户端代码百分百证明服务器内部是事件调度、固定逻辑帧，还是发射时立即结算。

## 3. 玩家能量炮的完整链路

### 3.1 开火时客户端先表现，再发送意图

`mainclient_me.fcc` 中的攻击入口顺序是：

1. 检查当前装备、冻结/干扰状态和地图边界；
2. 调用 `myaction(eqno, x, y, PkLock)`；
3. 武器 `Action(...)` 在本地扣除即时能量、截断到最大射程、播放炮身动作并创建子弹；
4. 本地动作成功后发送 `r_OnAction(eqno, x, y, PkLock)`；
5. 客户端自己启动武器冷却计时器，服务器另以 `OnActOK()` 确认动作通信完成。

这说明直线能量炮上报的是：

- 装备槽编号；
- 鼠标目标坐标；
- PK 标记。

它没有在发射请求中上报“我命中了怪物 X”。这与实际体验中“炮弹沿途会被第一个怪物接住”是一致的：服务端拥有发射者位置和所有怪物位置，必须自行找出射线方向上的首个合法目标。

### 3.2 客户端弹体如何飞行和“接住”

`bullet.fcc` 的 `laserbullet`：

- `line` 速度参数为 `1000`，不是 `1000 px/s`；运行容器的 `nMFly` 换算后默认有效速度约为 `416.667 px/s`；
- 使用 `line(x0, y0, x1, y1, m_nspeed, 8, "endfly")` 做直线飞行；
- 使用 `hittest := point(BULLET_HITID, "atattack", "onhit")` 做本地表现碰撞；
- `onhit` 默认会停止 `fly`、关闭 `hittest`、隐藏弹体并延迟删除；
- 聚能穿透等特殊状态会跳过上述删除，于是弹体可继续穿过目标。

所以玩家看到的“第一只怪物把子弹接住”，至少有一半确实是客户端完成的：客户端弹体的点碰撞会在接触目标时停止显示。

### 3.3 本地碰撞不再上报能量炮命中

关键证据位于 `npcbasecltmain.fcc`：怪物的 `atattack(obj pobj)` 第一条有效语句就是 `return`。旧代码中原本存在的 `r_Onatattack(...)` 已整体注释。

玩家对象的 `mainclient_char.fcc::atattack(obj pobj)` 也是同样结构：立即 `return`，旧的 `r_OnUserAtattack(...)` 已注释。

因此在当前荣耀客户端中：

- `laserbullet.onhit` 仍会让本地弹体消失；
- 被碰撞怪物的脚本不会据此通知服务器；
- 这次表现碰撞也不会直接调用怪物 `Damage(...)`；
- 真正的命中结算只能来自服务器根据先前 `r_OnAction(...)` 作出的判断。

这直接排除了“普通能量炮完全由客户端碰撞决定伤害”的解释。

### 3.4 伤害和命中特效由服务器一起返回

怪物收到的 `Onattack(harm, AviFileIndex, SoundFileIndex, BulletEffectPalette)` 会：

1. 用服务器给出的三个资源索引创建 `laserblast`；
2. 调用 `Damage(harm)`；
3. 刷新本地血条并显示伤害飘字。

`Damage` 只消费服务器传入的伤害值，不重新计算攻击、防御、暴击或命中。甚至某些超高血量怪物还带有纯显示用的倍率修正，进一步证明客户端血条是服务器结果的投影，而不是结算来源。

## 4. 其他弹体协议

原版不是一套统一的 projectile 协议，而是逐年扩展出来的多套规则。

### 4.1 火箭炮

`FireGunBullet` 的源码注释直接写明：“碰撞在服务端进行，客户端类只进行显示。”

它的流程是：

1. 客户端以速度参数 `1000` 飞向指定地图坐标；
2. 飞到终点时调用 `FireGunBulletBom(ownerId, x, y)`；
3. 该方法发送 `r_OnFireGunBulletBom(ownerId, x, y)`；
4. 服务端再广播 `OnFireGunBulletBom(...)` 供客户端播放范围爆炸；
5. 旧的本地环形 `hittest` 和 `FireGunBulletHit` 命中上报代码均已注释。

可确认服务端负责范围命中与伤害；但原协议仍让发射客户端在飞行结束时报告爆炸坐标，是一种旧式信任边界。复刻版不应接受客户端决定的最终爆点，而应由服务器根据发射时刻、方向、速度和最大距离推进到爆炸时刻。

### 4.2 追踪导弹

`MissileBullet` 与能量炮不同：

- 创建时持有明确的目标对象；
- 初始速度参数为 `600`；
- 基础导弹类在创建时读取目标当前位置并生成朝向该点的飞行表现；这一基础类没有看到周期性重新瞄准，另一些护卫导弹派生类才会每 500 ms 重算目标位置；
- 抵达目标后，只有发射者客户端发送 `r_OnMissileAttack(ownerId, missileIndex)`；
- 服务端随后以 `OnMissileAttack(harm)` 返回实际伤害。

因此导弹的“到达目标”在旧客户端中参与了上报，但客户端仍不能指定伤害值。这个入口在现代对抗环境中可以被伪造；复刻版应由服务端维护追踪目标和权威到达时刻，客户端只插值显示。

### 4.3 怪物炮弹

普通 `npcbullet` 和旋转弹 `npcbulletRoto` 都在客户端创建：

- `line` 速度参数为 `1000`，默认有效速度约为 `416.667 px/s`；
- 客户端沿 `OnNpcAttack(x,y)` 给出的终点播放；
- `npcbulletRoto` 会以 `(目标点 - 发射点)` 调用 `CalAngle`，再对 ALE 的每一帧执行 `RotoFrame(i, -angle)`；奥姆虫弹体的原图朝右，不能不旋转就沿任意轨迹平移；
- 本地 `hittest` 负责让视觉弹体在接触对象时消失；
- 荣耀版脚本中没有找到可完成伤害结算的 `Npcatattack` 实现；
- 玩家实际扣血由单独的 `OnNpcattack(harm, effect...)` 回调完成。

所以怪物炮弹和玩家能量炮具有类似的显示/结算分离：弹体是本地视觉对象，伤害是服务端结果。

## 5. 服务器究竟怎样算弹道

### 5.1 可以排除的方案

服务器没有必要跟随每个客户端的显示帧率逐帧推进子弹。显示帧率因机器而异，也不适合作为联网权威时钟。

普通能量炮又没有上报命中目标，因此服务器不可能只等客户端告诉它“碰到了谁”。它至少要使用自己的玩家、怪物和地图状态做一次空间判定。

### 5.2 仅凭客户端尚不能区分的三种实现

原服务端可能采用以下任一种：

1. **发射时解析首个交点，再按飞行时间延迟结算**：对直线弹最省成本，也最符合固定轨迹；
2. **固定逻辑帧推进弹体**：例如 10～20 Hz，每步做上一位置到新位置的扫掠碰撞；
3. **发射时立即结算，客户端仅延迟表现**：也能匹配现有接口，但远距离命中时伤害回包时序会暴露这种做法。

静态 FCC 能确认伤害权威在服务端，却不能确认上述哪一种是原服务端内部算法。

### 5.3 可用于最终确认的抓包实验

如果以后希望进一步还原原服时序，可在可登录的版本中做两组实验：

- 在相同网络延迟下，分别贴脸和在最大射程攻击静止怪物，记录 `r_OnAction` 到 `Onattack` 的间隔。若间隔随距离近似按 `distance / projectile_speed` 增长，说明服务端保留飞行时间；
- 发射后让另一只怪物在飞行期间进入弹道，或让原目标离开弹道。若结果随飞行期间的位置变化，说明服务端持续/分段重算；若只取发射瞬间位置，则更接近预先求交并延迟结算。

测试时必须以伤害回包时间为准，不能以本地命中特效时间为准，因为本地弹体碰撞本身就是预测表现。

## 6. 复刻版权威弹道方案

### 6.1 消息边界

直线武器的客户端请求不应携带目标怪物 ID，只需发送：

```text
FireWeaponIntent {
  input_sequence,
  map_instance_id,
  ability_id,
  aim_world_position,
  client_tick
}
```

服务端从已认证连接获取玩家 ID，并从权威状态取得：

- 发射者位置与炮口偏移；
- 装备中的武器和弹体定义；
- 冷却、即时能量、射程、速度、穿透次数；
- 当前地图内怪物、玩家和可阻挡弹体的场景碰撞体。

服务端产生：

```text
ProjectileSpawned {
  shot_id,
  owner_id,
  origin,
  direction,
  speed,
  maximum_distance,
  spawn_tick,
  visual_id
}

ProjectileImpacted {
  shot_id,
  target_id,
  impact_position,
  impact_tick,
  damage,
  target_health,
  impact_effect_id,
  died
}
```

伤害、剩余血量和死亡状态只能出现在服务端事件中。

### 6.2 直线炮采用发射时一次性连续碰撞

当前首批能量炮是直线、定速、不追踪、不反弹的普通弹，不需要在服务端逐帧维护弹体坐标。已采用的权威算法是：

1. 服务端从权威玩家位置、炮口偏移和客户端瞄准坐标构造有限线段；
2. 对当前地图每个存活怪物的圆形受击体求线段—圆相交参数 `t`；
3. 选择最小的 `0 <= t <= 1`，即弹道上最先“接住”炮弹的怪物；
4. 发射时冻结 `target_entity_id`、精确交点和 `impact_tick`，但不扣血；
5. 到达 `impact_tick` 后再确认目标仍属于该地图且仍存活，然后结算伤害；
6. 射线上没有目标时预约最大射程终点，到达后生成 `ProjectileExpired`，不造成伤害。

这样仍然是连续碰撞，不会因为一个逻辑步跨过小怪而漏判；区别只是直线轨迹可以解析求解，所以无需把同一条线重复切成 20 Hz 小段。追踪、反弹、加速或中途受场景影响的弹体仍应使用固定逻辑帧扫掠。

怪物碰撞体应围绕脚点设置独立的战斗圆或胶囊，不能直接使用整张精灵图的透明外框。遮挡子弹的场景对象应使用单独的 projectile collision layer；哪些地图物件能挡炮弹尚无荣耀版确证，应数据化而非写死。

连续线段检测可以避免速度较高的弹体在一个逻辑步内直接跨过小怪，这正是“看上去穿过却没接住”最常见的实现错误。

### 6.3 性能与权威边界评估

一次开火的成本是 `O(M)`，`M` 为当前地图存活怪物数；没有“弹体数 × 飞行帧数”这一维。即使按 100 名玩家、每秒 5 发、同图 100 只怪物估算，也只是约 5 万次简单线段—圆求交/秒。对几人私服的 D04 当前 16 只怪物而言，这一开销可以忽略。

当单图怪物达到数千只或出现大量机关碰撞体时，再用地图网格、四叉树或 BVH 先筛选线段经过的分区；协议和命中语义不需要改变。

不采用“客户端发射时上报矢量、命中时再上报怪物，服务器只做合理性检查”的方案，原因是：

- 客户端会实际取得目标选择权，可故意漏报前排怪物、延迟命中或重放命中；
- 所谓“是否过于离谱”最终仍需要服务器重算弹道，无法真正节省验证成本；
- 网络抖动会让命中上报时刻和怪物移动历史难以对齐；
- 服务端一次求交已经足够便宜，没有交换权威性的必要。

客户端只负责立即播放预测弹体和本地命中特效；扣血、目标、死亡、经验与掉落始终只认服务端事件。

### 6.4 客户端预测与校正

客户端点击后可立即创建预测弹体，以免等待网络往返：

- 预测弹体按本地视觉速度飞行；
- 本地碰撞可暂时停止弹体，但不能扣血、发经验或触发掉落；
- 收到 `ProjectileSpawned` 后，用 `shot_id` 绑定预测弹体；
- 收到 `ProjectileImpacted` 后，以服务器给出的目标与坐标为准；
- 本地预测若撞到 A、服务器判定撞到 B，应移除预测效果并在 B 处补播权威命中特效；
- 服务器拒绝开火时，撤销预测弹体，并以权威即时能量和冷却覆盖客户端显示。

私下几人联机无需逐帧广播弹体位置。直线弹只广播出生和结束事件，客户端便能重建轨迹；追踪弹可按较低频率同步目标或校正点。

## 7. 怪物移动、攻击、站立状态机

### 7.1 移动由服务端下发路径，客户端连续播放

基础怪物的远端创建接口带有当前位置、当前/最大血量、速度和 `NPCPath`。后续移动通过多个 `OnNpcWalkTo(...)` 重载下发：

- 完整路径字符串；
- 可选的本次移动速度；
- 可选的减速百分比和特效类型。

客户端把这些参数交给引擎的 `path(...)`，并切换本体和阴影到 `move`。这说明：

- 寻路目标和折线路径不是客户端怪物 AI 随机决定的；
- 客户端负责在路径段内平滑插值和选择对应方向帧；
- 网络不需要逐像素同步怪物位置；
- 服务端仍应以自己的逻辑帧维护权威位置，以便弹道和攻击距离判定。

### 7.2 站立是客户端动画机的回落状态

`path(...)` 的完成回调是 `StandPlay` 或 `BeginStandPlay`。回调会：

- 将阴影切回站立；
- 循环播放 `stand`；
- 不产生新的攻击、寻路或伤害请求。

所以“何时播放站立帧”可以由客户端在当前路径/攻击动画完成后自行判断；但服务端随时可以用下一条移动或攻击消息覆盖它。

### 7.3 攻击开始由服务端驱动

远程怪物收到 `OnNpcAttack(x,y)` 后才会：

- 面向服务器指定的目标坐标；
- 把本体和阴影切到 `action`；
- 播放攻击动画；
- 创建对应 `npcbullet`；
- 播放怪物开火音效；
- 动画结束后本地回到站立。

近战怪物的基类同样由 `OnNpcAttack(x,y)` 触发攻击动作，只是不创建普通远程弹体。感光质“贴到战车上攻击”可在复刻版表现为极短攻击距离的同一套权威状态机，而不需要交给客户端自行决定攻击。

感光质的白色覆盖效果不属于攻击开始阶段。服务端确认受击后调用玩家对象的 `OnNpcattack(harm, blasteffectfileIndex, ...)`；该函数先从 `m_szNPCBulletAvi` 取 ALE，再创建 `laserblast`。`laserblast` 的无坐标构造函数会读取当前玩家/战车坐标，把自身层级设为受击对象上一层，并以每帧 66 ms 播放，因此效果看起来直接罩在战车上。扣血和白光表现由同一个服务端回调触发，但伤害值仍由服务端给出。

荣耀版感光质类保留的旧命中特效名是 `CHN_2005_06_28_18_47_58_908.ale`，全局 NPC 命中特效表的索引 0 也指向它。荣耀下载清单不再保留这个旧路径，但活跃资源 `pic3/npc/CHN_2005_06_28_18_45_00_878.ale` 与其 MD5 同为 `5038ceae69659a9979fa38af07512bc4`，是同一份 5 帧白蓝覆盖动画。复刻版使用这个荣耀版活跃副本，不从免费版借图。退役服务端是否始终给三种感光质下发索引 0 无法仅靠静态客户端证明；三类共用该效果是基于客户端预留映射、内容哈希和实机记忆的高置信恢复。

### 7.4 推荐的复刻状态字段

服务端怪物快照至少包含：

```text
MonsterSnapshot {
  entity_id,
  position,
  facing_index,
  action,          // idle | move | attack | dead
  action_started_tick,
  action_sequence,
  health,
  max_health,
  alive
}
```

客户端以 `action_sequence` 去重。`move` 根据快照插值；`attack` 必须从首帧触发一次；没有新动作且上一动作播完时可本地循环 `idle`；`dead` 只能来自服务端事件。

## 8. 怪物死亡与死亡特效

### 8.1 死亡是独立的服务器生命周期事件

基础怪物的 `Damage(harm)` 在血量小于等于 0 时只会把显示值钳制到 0、刷新血条并显示飘字，不会调用 `OnDie()`。

`OnDie()` 则单独完成：

1. 创建 `laserblast(m_sdieblasteffectfile, m_sdieblastsoundfile, deathPalette)`；
2. 隐藏怪物本体；
3. 个别基类还会通知本地攻击者记录死亡位置。

这证明“最后一击伤害”和“怪物已死亡”是两件不同的客户端消息。复刻版也应让服务端原子地产生一次 `MonsterDied`，用 `death_generation` 或唯一事件号避免多人同时攻击时重复掉落、重复经验或重复播放死亡效果。

### 8.2 已找到的荣耀版死亡素材

首批四类怪物的逻辑映射如下：

| 奥姆幼虫 | `pic3/npc/OnDie/CHN_2005_06_28_18_39_07_820.ale` | `res://assets/monsters/om_larva/shared/effects/death/animation_frames.tres` |

## 9. 当前实现状态与剩余边界

### 9.1 玩家能量炮权威命中已完成

`UseAbilityIntent` 现在只接收地图、技能、瞄准坐标和输入序号，不接受客户端目标 ID 或伤害。`ProjectileSweep` 被服务端权威模块和客户端预测共同复用；服务端在发射时选择路径上的首个怪物，生成未来 `impact_tick`，到达前怪物生命保持不变。

空弹道会飞满射程后失效；两发同时在途的最后一击只会生成一次 `monster_died`。当前运行速度 520 px/s 是明确标注的复刻调参，荣耀退役服务端的真实常量仍未知。

### 9.2 客户端仍需补完整的 `shot_id` 校正

客户端和服务端已经使用同一连续求交公式，通常会得到相同首个目标；但当前预测弹体尚未按 `shot_id` 与 `ProjectileSpawned` 绑定，也没有在预测目标与权威目标不一致时强制迁移命中特效。

这不会再导致错误扣血，因为生命和死亡已经完全由服务端决定；它只可能在高延迟、怪物快速移动或未来加入场景弹体阻挡时造成短暂的视觉分叉。场景物件是否阻挡炮弹也仍缺荣耀版证据，尚未加入权威碰撞集合。

### 9.3 怪物死亡表现已完成

`MonsterDeathEffectController` 消费最后一击中的独立 `monster_died` 子事件。本体依权威快照隐藏，7 帧蓝白死亡爆散在服务器给出的原脚点作为独立节点播放；`death_generation` 和事件游标共同防止快照重发导致重复表现。

### 9.4 怪物攻击素材、到达时序与躲避判定已完成

怪物快照带 `action_sequence`，同一 `attack` 状态下的新一次攻击也会从首帧重播。奥姆虫、奥姆幼虫和毒胶按 `monster_attack_started` 使用各自荣耀版弹体素材；旋转弹会按权威起点到目标点的矢量设置节点角度。感光质保留 `contact_melee`：攻击开始时只播放身体动画，不伪造远程弹体；收到 `monster_attack_resolved` 后，才在受击战车位置播放 5 帧白蓝覆盖效果。

远程怪物发射时只冻结起点、朝向和旧瞄准点，不再冻结“必中的目标”。服务端以 20 Hz 将每颗在途弹体从上一位置推进到新位置；同一逻辑步内，还会取得玩家脚点的上一位置和当前位置，在相对坐标中做线段—圆连续求交。玩家受击圆当前采用脚点上方 16 px、半径 18 px，与现有动态角色碰撞尺度一致。这样既不会因弹体单步跨过战车而穿透，也不会因开火时曾经瞄准玩家而在其横向躲开后仍强制扣血。

第一次求交发生时才产生 `monster_attack_resolved` 并扣血；弹体抵达旧瞄准点仍没有碰到玩家时产生零伤害 `monster_attack_expired`。`impact_tick` 现在表示飞到旧瞄准点的最晚寿命，而不是预先承诺的命中时刻。多人同图时按交点参数选择路径上最先接触的存活玩家，因此另一辆战车也能实际挡下炮弹。

该方案每逻辑步的成本是 `O(P × A)`，`P` 为当前在途怪物弹体数，`A` 为同地图存活玩家数。20 Hz、8 名玩家、同时 100 颗怪物弹体时只有约 1.6 万次简单线段—圆求交/秒，对几人私服可以忽略；不需要按客户端 60/144 FPS 推演。以后单图达到数百玩家或数千弹体时，再按地图网格筛选候选玩家即可，协议和命中语义不变。

奥姆虫与奥姆幼虫当前共享 `416.666667 px/s`：该值来自对荣耀运行容器 `nMFly` 的反汇编换算，而不是把 FCC 的 `m_nspeed=1000` 直接当作像素/秒。完整公式、速度档与无弹道例外见 [monster_projectile_speed_reverse_engineering.md](monster_projectile_speed_reverse_engineering.md)。结算事件保留 `combat_actor_id` 与权威 `impact_position`，使表现层无需用中文名猜命中特效，并能在后续按权威接触点校正预测弹体。

## 11. 验收用例

至少覆盖以下行为：

1. 点击后方怪物 B，前方怪物 A 与弹道相交时，A 受伤且 B 不受伤；
2. 射线上没有目标时，弹体飞满射程后消失且无人扣血；
3. 高速弹体单逻辑步跨过怪物中心时，连续碰撞仍能命中；
4. 本地预测命中 A、服务器命中 B 时，最终血量和命中特效以 B 为准；
5. 伤害发生时刻与权威飞行时间一致，不在按下攻击键时立即扣血；
6. 两名玩家同时打出最后一击时，只产生一次死亡、经验、掉落和死亡动画；
7. 怪物收到路径后播放移动，路径完成后本地循环站立；
8. 怪物只有收到权威攻击状态/事件才播放攻击，动画结束可本地回站立；
9. `MonsterDied` 到达后本体隐藏，死亡效果在原脚点独立播完；
10. 怪物复活使用新的 `death_generation`，不会被旧死亡事件再次隐藏；
11. 玩家在怪物弹体接触前横向离开原瞄准线时不扣血，并收到无伤害失效事件；
12. 玩家或另一辆战车在两个逻辑 tick 之间穿过弹道时，移动线段连续求交仍能给出唯一的首次接触。
