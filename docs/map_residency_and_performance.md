# 地图按玩家驻留与模拟性能

## 加载边界

服务器启动只读取轻量地图路由/定义索引，不创建导航图、怪物种群或矿源。
玩家首次进入（含登录恢复、普通传送、击毁回城）才调用 `ensure_runtime_map`。
同图多个玩家共用一个实例，不按玩家重复创建地图。

每个逻辑 tick 开始前，注册表把无人且在途事务已结清的地图移出活跃集合：

- 停止地图 tick、怪物 AI、游荡寻路、采矿计时和种群补充；不向客户端发送空图快照。
- 释放 `DiamondNavigation` 和采矿模块持有的导航引用，解除战斗模块的地图回调。
- 只保留休眠领域状态：怪物位置/生命、矿点余量、地面掉落、时钟与生成序号。
- 返回时重新加载导航并恢复回调，不重新生成整张图。休眠期间不逐 tick 重放，
  只补算经过时间与刷怪/补矿周期，避免来回切图刷新血量或刷满已采过的矿。

休眠仍保留少量业务状态对象，并不等于销毁地图的全部数据；否则返回时会重置资源。
当前状态保留范围是本次服务器进程，尚不等同于地图世界状态的数据库持久化。

## 两个例外

1. 短线重连宽限期内，服务器仍保留玩家实体，因此这张图仍活跃；宽限结束移除实体后休眠。
2. 最后一个玩家离开时若有在途炮弹/怪物攻击或采矿事务，地图短暂继续结算。
   此时不再执行怪物 AI、发起新攻击或游荡，结清后下一 tick 休眠。

地图注册表的 `all_instances`、按实例 ID 和按地图 ID 查询只返回活跃实例。
调用方需要入图时必须走 `ensure_runtime_map`，不能直接取得休眠对象后使用其导航。

## 回归

`tests/server/map_residency_test.gd` 覆盖启动零实例、同图两人共享、最后离开释放导航、
导航弱引用回收、六分钟空图不模拟、回来保持血量/矿量/掉落、按周期补充以及在途攻击阻止休眠。
同时回归权威服、传送、击毁回城、采矿、存档恢复。
真实 ENet 独立服务器＋双客户端/重连、大厅→城区传送均通过；测试观察器同样遵循
首次玩家到达前地图实例可以为空的契约，不为测试预先加载目标地图。

这些是服务端模拟边界；客户端当前地图的纹理生命周期是另一层责任，不应把缓存的图片
或挂载内容包索引与“后台仍在模拟其他地图”混为一谈。

## 游荡/返巢寻路退化

另一个独立问题：怪物绕障碍暂时越过游荡半径后开始返巢，一跨回边界又继续原游荡目标，
两个方向交替且每次都重建路线。D03 同一只怪物在约 50 秒模拟内请求了 764 次路线。

`MonsterLifecycle` 现在持有显式返巢状态，返巢途中不被游荡半径或重新索敌打断。
抵达家点后清除旧目标并等待正常游荡间隔；失败路线也按该间隔重试，不每 tick 反复寻路。
这不改变怪物的主动攻击/被动反击/不攻击分类，也不改变移速、数量、伤害或弹道。

2026-08-31 无画面 CPU 探针：D03、100 怪物、一个固定玩家、20 Hz 模拟，关闭网络与存档。
修复前 45 秒墙钟只算完 998 tick，平均 45.11 ms、P95 119.28 ms；修复后
1,200 tick（60 秒模拟）耗时 1.12 秒，平均 0.94 ms、P95 1.48 ms。
这是模拟耗时，不包含客户端纹理加载与 GPU 渲染，不能直接换算为最终帧率。

## 长路线尖峰

怪物路径不再对每一个拐点从最终目标向前穷举可见性。无障碍直线直接使用两端点；
需要绕路时使用 AStar 原始路径，并限制每个锚点前瞻 24 个原始节点，所有输出线段
仍逐一验证可走。玩家的路径简化方式不变。

同一条 D03 的 283 点绕障路线，原简化阶段约 116 ms；新路线规划合计约 12 ms，
输出 22 点并通过全部线段阻挡检查（`tests/navigation/monster_route_planner_test.gd`）。

完成两项寻路修复后，连续 3,600 tick（3 分钟模拟）、每图 100 怪物加一个固定玩家：

| 地图 | 模拟单步平均 | P95 | 最慢单步 |
| --- | ---: | ---: | ---: |
| D03 | 0.86 ms | 1.29 ms | 47.07 ms |
| D04 | 0.82 ms | 1.31 ms | 7.87 ms |

D03 仍有少量不可达目标回退查询的尖峰，因此本次不宣称所有帧完全无卡顿。
上述探针为无画面测试；实际端到端帧率仍需在带渲染的游戏中观察。

## 2026-09-17 定时补怪时重复加载字体

普通怪每 60 秒补量。此前 `MonsterWorldView.configure` 为每只新怪物复制一份
`SystemFont` 并设置 700 字重，标签测量又立即触发系统字体加载。同一批补怪在主线程
重复执行，造成约十分之一秒的停顿；字体族相同并不意味着这些独立资源共用加载缓存。

名称字体现在由 `MonsterWorldView` 持有一份静态共享资源，仅首次创建时配置。
怪物回收、补量及切图不重新构造字体；仍使用原来的微软雅黑、700 字重、12px、轮廓和位置。
没有调整怪物数量、刷新周期、模拟频率或存档策略。

同机 Godot 4.7.2 无画面测试：使用真实 D03 权威快照和 `MonsterWorldController`，
首次生成 210 个视图，再连续五轮替换其中 10 个实体 ID，以测量资源已热身后的补怪开销。

| 客户端快照应用 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 首次创建 210 只怪物 | 2826.52 ms | 133.14 ms |
| 每批替换 10 只，五次范围 | 133.08～144.96 ms | 4.55～6.52 ms |
| 仅更新已有怪物 | 2.48～2.91 ms | 1.79～3.27 ms |

随后执行 3,600 个真实服务端 tick（3 分钟模拟），每分钟击杀一批制造补量，客户端按
10 Hz 接收快照。第 120/180 秒真实补怪快照处理分别为 5.06/7.54 ms，服务端对应单步为
5.55/6.95 ms。关闭网络、存档及战斗日志，未修改日常存档。探针记录保存在本地
`.godot/performance-client-before.log`、`.godot/performance-client-after-font.log` 和
`.godot/performance-full-after.log`，不提交临时日志。

这些是 CPU 路径计时，不是整帧渲染耗时：长测中首次攻击动画加载仍有 56.55 ms 尖峰，
前述 D03 不可达路线回退也仍有约 50 ms 尖峰，因此不宣称所有来源的顿帧均已消除。

`tests/client/presentation/combat/monster_hover_name_test.gd` 增加共享资源及回收后复用断言，
先在旧实现复现两项失败，再验证修复后 23 项通过，并纳入客户端总门禁。
OpenGL 实际渲染同样通过，确认名称仍为微软雅黑且位置、字重未变；阴影专项通过。
ALE 全种群动画专项 1675 项通过，同时去掉其过时的“仅有 21 种已投放怪物”假设，继续逐种
验证当前全部启用怪物的三种动作和八个方向。正式入口零 GDScript 警告/错误。

## 2026-09-17 怪物游荡错峰

此前首次游荡统一在地图第 100 tick，完成移动后固定等待 100 tick；运行中补怪也错误地
把 100 当作绝对截止时间。相同批次的怪物一起启动，失败寻路后仍然一起重试。

现在由 `MonsterLifecycle` 持有独立的计时随机序列：

- 首次等待在配置周期内均匀分布，默认 20 Hz / 5 秒配置即 1～100 tick。
- 走完、遇阻、重生后的等待为基准间隔的 75%～125%，默认 75～125 tick（3.75～6.25秒）。
- 每轮重新选择等待时间，最低一 tick；不是仅在开图时加一次固定偏移。
- 补怪以实际注册的模块时钟起算；服务端不再用统一时刻覆盖领域对象安排的重生等待。
- 失败返巢继续保留返巢状态，但重试采用个体间隔；索敌、反击、正常追击和进行中的移动
  不受空闲游荡等待限制。
- 地图唤醒时只把休眠时长加到原截止时间，保留各怪物剩余等待及活动路线；新补怪另行错开。

随机序列只由地图实例和怪物身份初始化，不消耗战斗伤害/掉落随机数，且不受怪物注册顺序影响。
配置中的 `wander_interval_seconds` 仍是基准值，种群数量、刷新周期和怪物速度均未改变。

`tests/server/combat/monster_wander_timing_test.gd` 在旧实现先复现集中启动，再验证修复：
200只相同配置怪物、1000 tick、导航固定失败以覆盖重复重试，单 tick 最大请求数由200降至8，
发出请求的 tick 数从10增加到864。6208项断言覆盖首次分散、持续变化、注册顺序独立、
运行中补怪、同批重生、不消耗战斗随机数、失败重试不饿死。该专项已加入客户端总门禁。

同一 D03 真实导航探针（210只初始怪物、3600 tick、相同玩家坐标及击杀节奏）：

| 指标 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 单 tick 寻路请求峰值 | 210 | 7 |
| 发出寻路请求的 tick 数 | 2256 | 2662 |
| 寻路请求合计 | 4924 | 4948 |
| 最慢模拟单步 | 62.14 ms | 49.48 ms |

请求数是固定场景实测，不是每 tick 的硬限额。单条不可达路线仍可能耗时约48ms，
错峰不会把单次同步寻路变成异步。探针不包含网络、存档或 GPU 绘制；没有调整日常存档。
