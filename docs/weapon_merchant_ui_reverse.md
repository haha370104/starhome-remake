# 武器商人、买卖与任务 UI 逆向记录

## 结论

本次实现没有套用 Godot 的现代化通用对话框，而是分别恢复原客户端的三种交互形态：

- 点击 NPC 后显示贴近 NPC 的 `BasePOPMenu` 纵向菜单；
- “买东西”和“卖东西”打开 530×450 的独立买卖窗；
- “中级任务”打开消息式任务窗口，由接受、材料进度和交付状态驱动。

界面仅发送操作意图。商品范围、价格、背包 revision、任务材料消耗与奖励都由权威服务器验证。

## 原客户端证据

### NPC 动作菜单

`starhome_lz_ry_fcc_source/baseclass/formbaseclass.fcc:3145` 定义了 `BasePOPMenu`：

- 高度按菜单项数量动态计算；
- 每一项是独立的文字按钮；
- 悬浮时切换为按钮发光色，按下时添加 glow；
- 菜单宽度按最长标题计算，并在两侧留白。

`starhome_lz_ry_fcc_source/sellorclt_style_hp.fcc:571` 的 `SellMenu1` 按 NPC 能力依次加入购买、出售、任务等动作。任务动作调用 NPC 的 `HandleWork`，而非打开一个全局任务列表。

### 买卖窗口

`starhome_lz_ry_fcc_source/sellorclt.fcc:638` 和 `:907` 分别定义 `SellDlg1` 与 `BuyDlg1`：

- 窗口尺寸为 530×450；
- 左侧物品滚动区位于 `(16, 84)`，大小约 295×314；
- 每项高度为 22 像素；
- 行内显示物品名、价格、数量和操作按钮；
- 鼠标进入时整行以黄色矩形高亮，并刷新右侧物品图与复杂说明；
- 原文字色为 `#FAF0C8`；
- 窗口可以拖动并被置顶。

原客户端对可合并物品另开数量输入窗。当前雏形按一次一个执行交易，协议已经保留 `quantity` 字段，后续可补数量输入而无需改变服务端模型。

### 循环任务

`starhome_lz_ry_fcc_source/sellorclt.fcc:254` 定义武器商人任务；任务消息由 `ShowTaskMessageWnd` 创建，确认按钮调用 NPC 的 `HandleEve`。原任务要求为：

- 低级类胶 20 个；
- 低级能量催化剂 20 个；
- 低级生物硅 20 个。

基础奖励为 1500 金币，最多完成 30 次；第 5、10、15、20、25、30 次分别给出加强能量炮、改式引擎、领航者战车、突袭能量炮、多能引擎、勇敢者战车。对话原文来自 `starhome_lz_ry_fcc_source/great/code_string.fcc:457-460`。

## 复刻实现

- `HallHud` 只负责 NPC 附近的小型动作菜单；右键点击菜单会关闭且不会触发地图移动。
- `WeaponMerchantWindow` 根据 `buy`、`sell`、`task` 三种模式渲染原版布局。
- `GameWindowManager` 统一管理窗口置顶、拖动、右键关闭与命令分发。
- `AuthoritativeCommerceService` 依据会话绑定的玩家存档执行交易和任务，不接受客户端提交价格、奖励或玩家身份。
- 商店动作复用现有 `player_panel_command` 通道，响应仍是同事务的人物、背包、战车和 commerce 快照。

当前普通商店按引擎、战车、能量炮、挖掘臂、维修臂分组，并在组内按使用等级递增排列；等级上限为 280。车、炮、引擎使用已核对的官网型号白名单。商品图标通过统一物品表现目录按需解析。

## 2026-09-07：价格核对与地面挖掘臂范围

已核对荣耀源码、导出目录和商店取价：`cltobj/equipcltclass.fcc` 的 `tank7/tank8`（230/270级）、
`engine7/engine8`（220/260级）、`gun8/gun9`（240/280级）都明确设置
`m_nWorth=2000; m_nSell=1000;`。例如战车在源码 376–377、438–439 行。
`sellorclt.fcc:691` 创建商品对象，738 行展示 `m_nWorth`，765 行把该值提交购买。
因此目前的 2000 并非导出漏位或手工填错；尚无证据可以把别的数值认定为该版本原版价格。

用户确认复刻版继续按前档逐档翻倍，回收价取售价的一半：

| 装备类别 | 前档售价基准 | 第一档新售价 / 回收价 | 第二档新售价 / 回收价 |
| --- | --- | --- | --- |
| 战车 | 190级，50,000 | 230级：100,000 / 50,000 | 270级：200,000 / 100,000 |
| 引擎 | 180级，25,000 | 220级：50,000 / 25,000 | 260级：100,000 / 50,000 |
| 能量炮 | 200级，40,000 | 240级：80,000 / 40,000 | 280级：160,000 / 80,000 |

此决策存放于 `data/gameplay/commerce/equipment_pricing_v1.json`，标注 `remake_design`。
`WeaponMerchantCatalog` 在初始化时验证定义 ID 与整数价格，所有商人共用该配置。
商品列表、回收列表、权威买卖结算均从这个目录取价，客户端传入的价格不能影响扣款。
原始物品目录及 `legacy_properties` 保持源码证据；该配置只调整交易价格，不重写装备的维修材料、耐久或战斗属性。
下次服务初始化即采用新价，既有物品无需迁移或重新生成。

地面挖掘臂原版类别为 `m_nEquipKind2=4`，太空挖掘臂为 `102`，见
`cltobj/equipclt.fcc:35–36`。商品白名单现仅保留普通地面 `Collector` 至 `Collector7`：
初级（10）、改式（30）、精度（60）、多空（100）、磁性（150）、电磁（200）、磁导（250）。
排除太空的切割、艾克雷特、鼹鼠 I 型挖掘臂；同时排除非本期普通升级序列的
`Collector1000` 激光切割挖掘臂（该特殊型号本身仍属地面，不能误记为太空）。
300级以上普通地面型号亦不在本期等级范围内。原始目录保留这些已解析记录供研究与既有存档解析，
商店显示及权威购买请求均以在售白名单为准。

回归已接入 `tools/run_project_checks.ps1`：商人领域测试覆盖六件装备价格、跨商人回收价和七款挖掘臂；
商店运行时测试覆盖实际扣款、资金不足、跨商人出售，以及直接伪造购买请求也不能购入未上架的挖掘臂。

### 地面维修臂注册修正

`starhome_lz_ry_full_parsed/catalogs/equipment_catalog.json` 中，`repair` 至 `repair6`
的基类为 `Repair`、目录分类为“武器”，因此导出到领域目录后是 `vehicle_weapon`；
`space_repair_*` 的基类为 `space_repair_base`、分类为“其他装备”，对应 `vehicle_equipment`。
此前商店只在后者中匹配“维修臂”中文名，导致普通地面型号全部漏售、太空型号错误上架。

现在工程臂分组同时识别这两种领域类型，并读取 `m_nEquipKind2`：3 为地面维修臂，4 为地面挖掘臂；
太空的 104/102 不进入这两个商品组。维修臂白名单仅登记当前 280 级上限内的六款普通 `Repair` 子类：

| 原始类（仅溯源） | 名称 | 使用等级 | 售价 |
| --- | --- | --- | --- |
| repair | 初级维修臂 | 10 | 500 |
| repair2 | 加强维修臂 | 50 | 5,000 |
| repair3 | 精密维修臂 | 100 | 10,000 |
| repair4 | 超导维修臂 | 150 | 20,000 |
| repair5 | 磁性维修臂 | 200 | 25,000 |
| repair6 | 电磁维修臂 | 250 | 60,000 |

价格沿用原始目录，未套用车、炮、引擎的六项价格调整。列表仍排在挖掘臂之后并按等级递增。
领域回归核对完整型号、等级、价格和原始继承链；交易回归逐项购买六款地面维修臂，核对实际扣款与背包物品，
并确认直接提交 `space_repair_2` 至 `space_repair_5` 的购买命令也会被权威服务拒绝。
